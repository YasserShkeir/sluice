How each engine decides what it is allowed to see

Engine A — MITM proxya local HTTPS proxy you route a client through

interceptor/src/mitm-engine.ts

Routed client

Browser via the macOS system proxy, or a desktop app launched with --proxy-server=127.0.0.1:8080.

TLS scope decision

Default: decrypt every host. Any --host / interceptHosts entry — or interceptAllHosts: false — narrows it to the adapters' hosts plus those, each with a *.host wildcard.

In scope → decrypted

Passed straight through, never rewritten. Text bodies only, capped at 5 MB. WebSocket text frames become their own captures.

Out of scope → tunnelled

CONNECT'd as raw bytes. Sluice cannot read it, so it cannot store it — a stronger guarantee than redacting it afterwards.

Engine C — CDPsluice capture

cdp-engine.ts

Attach, don't proxy

Chrome runs with --remote-debugging-port=9222 and its own profile. The engine issues no requests of its own — no CA, no proxy.

XHR / Fetch only

One CDP client per page target, re-scanned every 2s. Documents, scripts, images, media and beacons are dropped before a row exists.

Engine C — extensionserve --ingest

packages/extension

Two worlds, one bridge

MAIN-world patch of fetch/XHR → postMessage → ISOLATED-world bridge that re-validates and re-clips at 512 KiB.

Default-deny hosts

The MV3 worker sends nothing until an endpoint, an ingest token and an explicit host list are set. Batches of ≤500, flushed at 50 or 2s.

Slack

The xoxc token from Slack desktop's LevelDB plus the d cookie, decrypted with the Slack Safe Storage Keychain item.

Trello · Loom · LinkedIn

Chrome's per-profile cookie DB via Chrome Safe Storage; LinkedIn also derives a csrf-token from JSESSIONID. Gmail and fast.com need none.

What Engine A keeps separateeach step is its own deliberate command

Generating the CA

sluice start mints sluice-ca.key/.cert under Application Support if they are missing. That alone decrypts nothing.

Trusting the CA

sluice ca-install adds it to the login keychain — a separate, deliberate step, reversed by ca-uninstall.

Isolating the engine

serve --isolated runs the proxy in its own process, speaking NDJSON over fd 3. It carries no adapters: attribution and parsing stay in the parent.

Every engine redacts at its own boundary — redactUrl, redactHeaders, redactText — before the capture leaves the module, and the runner redacts again on ingest. Attribution is separate: an unrecognised service is stored with adapter_id NULL rather than dropped.
